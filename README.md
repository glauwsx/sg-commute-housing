# sg-commute-housing

輸入你的上班地點，找出新加坡通勤最方便的租屋區域。上班地點、通勤方式、廠車點全部可以自己設定。第一次打開停在 **City Hall（政府大廈站）** —— 刻意選一個不屬於任何人的地點，側欄會標「示範用的預設地點」，直到你換成自己的。介面有**中文／English** 兩種語言，右上角切換。

作者自己的設定（上班地點＋四個廠車點）存在 `data/processed/preset-author.json`（不進 git），要用時：

```bash
cp data/processed/preset-author.json data/processed/setup.json
```

**這是一個本地 web app，全程在介面上操作** — 輸入 API key、下載資料、搜尋公司地址、增刪廠車點、開關通勤方式、調參數、匯出結果，都在同一個畫面裡完成，不需要先跑腳本再看檔案。

## 核心模型：接駁腿 × 終點

一趟通勤被拆成兩個獨立的軸，所以不需要列舉一堆組合：

| | **終點＝公司** | **終點＝廠車點** |
|---|---|---|
| **走路** | 住超近 | 🚐 走路去搭廠車 |
| **搭公車** | 🚌 公車直達 | 🚐 公車＋廠車 |
| **搭捷運** | 🚆 捷運直達 | 🚐 捷運＋廠車 |
| **先搭一小段再換車** | 🔁 轉乘一次到公司 | — |

側欄的四個勾選項就是這張表：🚌 公車直達、🚆 捷運直達、🔁 轉乘一次、🚐 廠車（底下再拆成走路／公車／捷運三個接駁開關）。**每一項都可以單獨關掉**，關掉就真的不列入推薦計算，不是只把圖釘藏起來。

⭐ 的門檻另外選：`符合任一種` / `至少兩種` / `全部都要`。只勾一種方式時「至少兩種」會自動降為 1，不會給你一個空清單。

每一種走法都會算出**估計的門到門分鐘數**（怎麼算的見下面「估計時間怎麼算」），🚌🚆🔁 超過「單程最多幾分鐘」就不算數 —— 公車直達但要坐 80 分鐘，不該跟 20 分鐘的直達公車一樣拿星。

## 快速開始

```bash
cd projects/sg-commute-housing
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python app.py
```

瀏覽器會自動開啟 http://127.0.0.1:5000，然後照畫面上的三個步驟走：

1. **貼上 LTA DataMall API Key** → 按「驗證並儲存」。驗證成功會自動寫入 `.env`，之後不用再輸入。
   - 免費申請：https://datamall.lta.gov.sg/ → 註冊 → 申請 API Access Key（信箱收信）
2. **按「開始下載」** → 抓取全新加坡公車路網（約 5,000 站牌 / 26,000 筆路線站序）與捷運／輕軌站點（約 190 站），有進度條。只需下載一次，之後快取在 `data/raw/`。
3. **按「進入探索器」** → 開始互動分析。（之後再開 app 會自動跳過前兩步）

## 側欄長怎樣

最上面是**上班地點卡片**（名稱＋地址，右邊一顆「更改」），每個新使用者第一件事就是改它，所以還停在預設值時會自己打開。接著是**通勤方式四個勾選、單程上限、⭐ 門檻**，再來是結果。其餘收在可展開的區塊裡（更多設定、廠車上車點、診斷數字），展開狀態會跟著設定一起存。

**能收合的東西只有兩種長相**，看過一次就認得：

| | 長相 | 用在 |
|---|---|---|
| 整個區塊 | 灰底框、標題右邊寫著目前的值（例「接駁 5 分 · 步行 400 m」）、最右邊一個 ⌄，打開後變 ⌃ | 更多設定、廠車上車點、診斷數字 |
| 卡片裡的「看更多」 | 綠色字＋▾，像連結 | 「顯示其餘 N 條」、「ⓘ 時間怎麼算的」 |

不能收合的標題（「怎麼去上班」「住家試算」）是灰色小字＋底線，兩者不會長得一樣。舊版的可收合標題是一般文字配 10px 的 ▸，看起來像清單的圓點，分不出哪些能點（2026-09-23 使用者回報）。

2026-09-23 同一天改了兩次。第一次依人因工程原則把控制項收起來（當時算法：一眼看到 49 → 16 個、側欄 2.9 → 1.5 個螢幕）；第二次改收起來之後「看不看得出能點」。第二次的前後用 `?audit` 量（見下面「怎麼評估好不好用」）：

| | 第二次改之前 | 改之後 |
|---|---|---|
| 看起來不像能點的收合標題 | 4 / 4 | **0 / 3** |
| 換上班地點要先點幾下 | 1 | **0**（還是預設值時自動打開） |
| 一眼看到的控制項 | 12 | 13 |
| 側欄長度，桌機 1280×800 | 1.41 螢幕 | 1.57 |
| 側欄長度，手機 375×812 | 3.01 螢幕 | 3.21 |

框線讓側欄多了約 0.2 個螢幕，換來每個收合區塊都認得出來。（`?audit` 的控制項算法比第一次嚴格：收起來的區塊裡的東西不算，所以是 12 不是 16。）

## 探索器能做什麼

| 操作 | 效果 |
|---|---|
| **搜尋地址** | 用 OneMap 查地址／大樓／郵遞區號／捷運站，**同名多筆會列出來讓你選**，不會默默挑第一個 |
| **公司名稱欄位** | 自己命名；一旦手動改過，之後搜尋地址就不會再覆蓋它 |
| **座標欄位** | 直接貼 `lat, lon`（會擋掉不在新加坡範圍的座標） |
| **拖曳上班地點圖釘** | 換地點，四種通勤方式與優先候選全部重算。名稱會自動變成「XX 站附近」（最近的捷運站 600m 內，否則最近的公車站）—— 除非你自己在名稱欄打過字 |
| **中文／EN** | 側欄右上角切換語言，記在這個瀏覽器；沒選過就跟瀏覽器語言。AI 模式也讀得懂英文句子 |
| **點地圖任一處** | 假設你住在那裡，右側即時列出四張卡片：直達公車、直達捷運、轉乘走法、可到的廠車點。每種走法都標**估計分鐘數**，依快慢排序；公車另標幾分鐘一班，廠車點另標「幾點前要出門」 |
| **四個通勤方式勾選** | 開關 🚌🚆🔁🚐；🚐 底下再獨立開關「走路／先搭公車／先搭捷運」去搭廠車 |
| **⭐ 門檻** | 任一種 / 至少兩種 / 全部都要 |
| **拖曳廠車圖示** | 換上車點，自動同時吸附到最近的公車站牌**與**最近的捷運站（400m 內） |
| **每個廠車點的核取方塊** | 單獨停用某個上車點（例如那班車你搭不到），其他照算 |
| **廠車上車點區塊** | 可收合（預設收起來）；沒有廠車的人直接把 🚐 取消勾選，整個區塊就消失 |
| **＋ 新增廠車點** | 按下後在地圖上點一下即可新增；名稱與發車時間可直接在側欄編輯，也可刪除 |
| **AI 分頁** | 打一句話就套用條件；標籤列出 AI 理解到什麼，可逐一拿掉 |
| **拉桿** | 公司周邊半徑、住家步行半徑、接駁最多搭幾分鐘（2→20 分，只算坐在車上，🔁 與 🚐 共用）、單程最多幾分鐘（20→120，最右＝不限）、捷運允許轉線次數（0→2） |
| **只看這條直達路線** | 從所有直達公車路線中隔離出單一條 |
| **只畫這個位置用得到的路線** | 選定住處後用這個。地圖只留下你點的那個位置實際搭得到的公車／捷運／廠車點，虛線標出要走去哪一站，⭐ 暫時隱藏。以預設設定實測：路線圖層 1,090 → 265、廠車可達圈 57 → 1 |
| **清除試算點** | 移除地圖上的試算位置，回到全域檢視 |
| **跳到優先候選** | 地圖自動縮放到所有 ⭐ |
| **儲存目前設定** | 存到 `data/processed/setup.json`，下次開 app 自動沿用 |
| **匯出候選 CSV** | 把目前設定下的候選區域下載成 CSV（含 BOM，Excel 開中文不亂碼） |

⭐ = 符合門檻的地點，候選單位同時包含公車站牌與捷運站。側欄依「HDB 鎮 ｜ 街道」分組列出，標出各組符合哪幾種方式與最快幾分鐘到公司，快的排前面；匯出的 CSV 也多了 `BestMinToWork` 欄。

## AI 模式：把一句話變成篩選條件

側欄上方有「手動／AI」兩個分頁。手動就是原本的拉桿；AI 分頁讓你直接打一句話，例如：

> 45 分鐘內到公司、不用轉車、班次要多、不要 Woodlands，最好月租 2000 以下

**AI 只做選擇題，不挑地點。** 它把句子對應到手動模式那幾個選項，地點一律由程式在全島 5,400 個站點上算。畫面會把「理解成這些條件」列成標籤，每個標籤都可以按 ✕ 拿掉（拿掉後拉桿回到你原本的值）。沒有資料的條件（租金、學校、熟食中心…）會單獨列出來，明講「沒有篩」。

分工是實測出來的（2026-09-22，10 句話、118 個欄位）：

| 判讀方式 | 答對 |
|---|---|
| 只用程式規則 | 111 / 118 |
| 規則 ＋ 本機 qwen3.5:9b | 117 / 118 |

- **數字、時間、地名交給程式**：小模型最容易錯的就是這些（「一個半小時」被讀成 30 分）。分鐘、走路幾分鐘、幾點出門、地區名（中英文都認）全部用規則讀。
- **AI 只答 7 題選擇題**：要哪些通勤方式、⭐ 門檻、要不要轉車、班次密不密、要不要靠近捷運、哪些區要／不要、哪些條件沒有資料。
- **AI 的答案要有依據才採用**：句子裡沒提到「轉、換」，就不接受「不轉車」；句子裡沒出現的地區也不會被篩掉。反過來，句子明說「可以接受轉乘」時，AI 說「不轉車」也會被否決。

跑在哪裡：

| | 誰回答 | 需要什麼 |
|---|---|---|
| `python app.py` | 本機 Ollama（`qwen3.5:9b`，約 9 秒一句）優先 | Ollama 有開就好，不用金鑰，句子不會離開你的電腦 |
| 同上，本機沒開 | Gemini 免費層（lite 群，約 5 秒） | `.env` 的 `GEMINI_API_KEY`，可在 AI 分頁貼上 |
| `output/explorer.html`（給別人） | Gemini | 對方自己的免費 key，存在他的瀏覽器，**不會寫進檔案** |

- 模型與位置可在 `config.py` 改：`OLLAMA_HOST`、`OLLAMA_MODEL`、`AI_MODELS`。
- Gemini 免費層會塞車：2026-09-22 實測四個 lite 模型有三個回「目前需求量過高」（503）。因此每個模型最多等 15 秒就換下一個，也因此本機模型排在前面。
- 找到結果後可以按「請 AI 比較前 5 名」，它只會根據算出來的數字寫 3–5 句比較，不會自己編。

## 怎麼評估好不好用

「好用」拆成三個問題，各有各的量法，不能互相代替：

| 問題 | 量法 | 什麼時候做 |
|---|---|---|
| **找得到嗎？**（控制項藏多深、看不看得出能點） | 網址加 `?audit`（例 http://127.0.0.1:5000/?audit）→ 右上角出現表格：每個常見任務要先點開幾層、在側欄第幾個螢幕、有幾個收合標題看起來不像能點 | 每次改版面後。幾秒鐘，可重跑，但只量結構 |
| **看得懂、做得完嗎？** | 找 5 個沒看過的人，給他們 5 個任務（換上班地點、找 45 分鐘內不轉車的區域、說出某個區域怎麼去上班、加一個廠車點、匯出清單），只看不教，記錄卡住的地方；做完填 SUS 問卷（10 題，0–100 分，68 是平均） | 大改之後。5 個人大約能找到八成的問題 |
| **算得準嗎？** | 從 ⭐ 清單抽幾個點，用 Google 地圖（平日 08:00 出發）比對門到門分鐘數 | 改 `TIME_MODEL` 或換預設地點後 |

`?audit` 量不到「字看不看得懂」—— 那只能靠真人。AI 代理人走查也抓不到「看起來能不能點」：它讀的是網頁結構，`<details>` 在結構裡本來就標明可展開，跟人眼看到的不一樣。

**準確度抽查（2026-09-23，上班地點 City Hall，⭐ 清單依快慢等距抽 5 點）：**

| 住處 | 模型 | Google（08:00） | 差 |
|---|---|---|---|
| Orchard Turn（捷運 NS） | 14 分 | 12 分 | +2 |
| Upp Boon Keng Rd（捷運 EW） | 15 分 | 16 分 | −1 |
| Stirling Rd（捷運 EW） | 22 分 | 25 分 | −3 |
| Clementi 站（捷運 EW） | 29 分 | 29 分 | 0 |
| Portsdown Rd（公車 14 直達） | 56 分 | 63 分 | −7 |

捷運直達四個點誤差都在 ±3 分內；公車長程穿過市區尖峰時少估了 7 分（只有一個樣本，還不夠改 `busKmh`）。另一個發現：Portsdown Rd 用 Google 換一次捷運只要 36 分，但預設「捷運不轉線」時模型只看得到 56 分的直達公車 —— 住西邊、上班在市中心的人，應該把「捷運內部允許轉線」調到 1。

## 估計時間怎麼算

**門到門分鐘 ＝ 走路 ＋ 等車 ＋ 坐車（＋ 換車）**，全部是估計值，參數在 `config.py` 的 `TIME_MODEL`，都可以改：

| 部分 | 怎麼算 | 資料來源 |
|---|---|---|
| 走路 | 直線距離 × 1.3 ÷ 80 m/分 | 1.3 是繞路係數，沒人能穿過組屋直線走 |
| 等公車 | 早上尖峰班距的一半 | LTA `BusServices.AM_Peak_Freq`（沒有就用離峰或下午的；22 個變體完全沒有，用 6 分） |
| 坐公車 | 路線上兩站的距離 ÷ 17 km/h | LTA `BusRoutes.Distance`（每一站距起點幾公里，原本就有下載，只是之前沒用） |
| 等捷運 | 3 分 | |
| 坐捷運 | 站與站直線距離相加 ÷ 28 km/h | 直線比實際軌道短，所以速度看起來偏低 |
| 捷運轉線 | 每次 5 分 | |

兩個速度是 2026-09-22 用 Google 地圖（平日早上 8:00 出發）校正的：

| 路段 | Google | 模型 |
|---|---|---|
| 捷運 Pasir Ris → Tuas Link（東西線全線） | 102 分 | 100 分 |
| 捷運 Punggol → HarbourFront | 41 分 | 40 分 |
| 捷運 Tampines → Raffles Place | 36 分 | 35 分 |
| 捷運 Woodlands → Ang Mo Kio | 24 分 | 30 分 |
| 公車 3 號 Punggol Int → Pasir Ris Int（含等車） | 41 分 | 46 分 |
| 公車 69 號 Bedok Int → Tampines Int（含等車） | 31 分 | 30 分 |

捷運原本想用「東西線全線約 1 小時」（Simple Wikipedia）推出 40 km/h，實測快了 35%，所以改成 28。公車用過網路上「平均約 15 km/h」的說法，長路線會多估 10 分鐘，所以改成 17。**寧可多估不要少估**：通勤時間被低估，比被高估更傷。

整段比對（住 Tampines St 41 → Raffles Place）：模型 44 分；Google 捷運段 36 分，加上走到站、等車約 42–44 分。

「只算站數」為什麼不夠：全島 26,073 段站距，搭 3 站的距離從 0.9 km 到 1.8 km（p10–p90）差一倍；早上尖峰有 78 條路線 20 分鐘以上才一班。以 Tampines 市中心為例，4 條直達公車從 23 分鐘（68 號）到 43 分鐘（3 號）都有，以前看起來一樣好。

所有比對運算都在瀏覽器端即時做（整個公車＋捷運路網一次載入到前端）。全島約 5,400 個站點每次都會重跑一遍「住在這裡的話有哪些走法」，靠的是一個網格空間索引，實測一次完整重算約 30–50ms，所以拖曳、拉桿都是立即反應。後端只負責下載資料、地址查詢代理與儲存設定。

## 實際分析結果（2026-08-24 跑真實資料，候選數 2026-09-22 更新）

資料量：5,208 個站牌 / 26,881 筆路線站序 / 806 條路線（803 個 (路線,方向) 變體）＋ 190 個捷運/輕軌站、12 條線。

以作者在 Pasir Ris 工業區的上班地點（當時的預設，現在是 `preset-author.json`；步行 400 m、門檻「至少兩種」）為例，開關不同通勤方式的候選數量：

| 勾選的方式 | 舊版：接駁 1 站、不限時間 | 新版：接駁 5 分、單程 60 分 |
|---|---|---|
| 公車直達 ＋ 捷運直達 ＋ 廠車（預設） | 81 | 138 |
| 同上，單程改 45 分 | — | 101 |
| 同上，單程不限 | — | 161 |
| 上面再加 🔁 轉乘一次 | 1,173 | 895 |
| 只勾 🔁 轉乘一次（門檻自動降為 1） | 1,931 | 1,397 |

新版預設比舊版多，是因為接駁從「1 站」放寬到「5 分鐘」（約公車 3 站）；單程 60 分鐘的上限則刷掉了 23 個「有直達、但要坐太久」的地方（161 → 138）。🔁 仍是四位數，這就是它預設關閉的原因：只要允許轉一次車，全島大半地方都到得了公司，⭐ 就失去鑑別度。

## 兩種跑法：自己用 vs. 給別人用

| | `python app.py` | `output/explorer.html` |
|---|---|---|
| 對方要裝什麼 | Python + 套件 + 自己申請 LTA API key | **什麼都不用**，用瀏覽器打開就好 |
| 怎麼給人 | 對方得自己 clone 跑起來 | 傳一個 0.9 MB 的檔案（AirDrop／email／丟雲端） |
| 地址搜尋 | ✅ | ✅（直接打 OneMap，需要網路） |
| 儲存設定 | 存到 `data/processed/setup.json` | 存在對方的瀏覽器裡（localStorage） |
| 資料新舊 | 隨時可重新下載 | 產生檔案當下的快照 |
| 更新資料 / 換 API key | ✅ | ❌（要重跑一次 `main.py` 產生新檔） |

**想給更多人用就用單檔版。** 它是把 web app 的同一份 HTML/CSS/JS ＋ Leaflet ＋ 整份路網資料內嵌後產生的（`src/export_webapp.py`），所以互動邏輯只有一份實作，不會兩邊行為不一致。除了地圖底圖與地址搜尋需要連網，其餘完全不依賴外部資源 —— 匯出時會檢查產生的 HTML 有沒有殘留 `/static/` 或 unpkg 的連結，有就直接報錯，避免生出一個「在你電腦上好好的、傳給別人就壞掉」的檔案。

產生方式：

```bash
python main.py            # 用你儲存的設定跑一次（沒存過就用 config.py 的種子值）
python main.py --refresh  # 強制重新抓資料
```

**先在 app 裡按「儲存目前設定」，再跑 `main.py`。** 有 `data/processed/setup.json` 時，上班地點、半徑、通勤方式勾選、廠車點（含停用的那些）都以它為準；沒有才退回 `config.py`。單檔版也會記下自己是用哪一份設定產生的 —— 你重新匯出、但瀏覽器裡還留著上次自己存的設定時，開檔會跳一行提示告訴你畫面上是哪一份，按「重設」可切回內建版本。

會產生 `output/explorer.html`（單檔版探索器）、`output/map.html`（folium 靜態地圖）、`output/candidates.csv` / `.md`（表格）。

單檔版少掉的只有需要後端的兩件事：API key 設定與重新下載路網。

## 邏輯說明

- **🚌 公車直達公司**：以公司座標為中心找半徑內所有站牌，再找出所有「路線站序中包含這些站牌」的 `(ServiceNo, Direction)` 組合。只有排在公司站牌**之前**的站才算上得了車 —— 之後的站在這個方向是離公司越來越遠（另一個方向的變體會涵蓋它們）。LTA 本身就把去程/回程拆成 Direction 1/2，快車或短程變體也會有自己的 ServiceNo（例如 `39` 與 `39e`），所以用這個 key 分組即可確保雙向與各變體都分開列出、不會合併。
- **路線名稱**（`src/route_labels.py`）：`Direction` 只是 LTA 內部的 1/2 代號，直接顯示成「往1」對讀者毫無意義，所以每個變體都改用 `BusServices` 的 `DestinationCode` 命名成「3 往 Punggol Int」。806 條服務裡有 227 條是**迴圈路線**（起點＝終點），終點站說明不了什麼，改用 `LoopDesc` 標最遠點 →「15 循環（經 Marine Parade Rd）」。803 個路線變體全部對得到，對不到的話會退而用該變體自己的最後一站。
- **🚆 捷運直達公司**：捷運沒有免費的座標 API，站點是從 OneMap 的搜尋 API 撈的（`src/rail.py`）。關鍵在於**站碼本身就編碼了路線與順序** —— `EW24` = 東西線第 24 站 —— 所以把同一個字首的站碼依數字排序，就重建出該線的實際行車順序，不需要任何時刻表資料。「同一條線 = 不用轉乘」與「搭 N 站」都由此推出。允許轉線 1～2 次時，會從公司所在線出發，沿著共用站點往外擴張；每個站記下「最快幾分鐘到公司」與那條最快走法轉了幾次。
- **🔁 轉乘一次到公司**：先定義「終點接口」= 所有直達公車會經過的站牌 ＋ 所有直達捷運線上的站。任何站點只要走 300m 內能碰到一個終點接口，就是轉乘樞紐；坐車 N 分鐘內能搭到某個樞紐的地方，就符合這個方式（時間算到公司門口，包含第二段）。同一條規則同時涵蓋了「接駁公車轉捷運」「捷運轉直達公車」「公車轉另一班公車」。**第一段一定要短**（受「接駁最多搭幾分鐘」限制）—— 因為「轉一次車、隨便搭多久」對新加坡幾乎每個地址都成立，那樣算出來的推薦沒有意義。
- **兩個階段，兩種視圖**：⭐ 回答「該往哪裡找」，勾選「只畫這個位置用得到的路線」則回答「決定住這裡的話，我怎麼去上班」。後者會把 ⭐ 一併隱藏 —— 它屬於前一個階段，留著只是雜訊。取消勾選即可回復。
- **住家試算的廠車卡片**：走路／公車／捷運**各列一種走法**，不是只列站數最少的那一個。跨模式比站數沒有意義 —— 捷運一站約兩公里、公車一站約四百公尺（全島 26,073 段站距的中位數，2026-09-22 實測），只取最小值會讓公車在有捷運可搭時整個消失。
- **🚐 廠車**：上車點是一個**地點**，不是一個站牌代碼 —— 只要下車後走一小段就到得了（公車 300m / 捷運 500m），那個站牌或車站就算「可以在這裡下車」。從這些下車點往回推到坐車 N 分鐘的地方，就是可達範圍。🚐 的時間只算到上車點 —— 廠車本身開多久是公司的班表，這裡不知道；所以 🚐 不受「單程最多幾分鐘」限制，但卡片會用發車時間倒推「幾點前要出門」。公車有方向性（只取路線站序中在它之前的站），捷運兩個方向都跑所以前後都算。走路／公車／捷運三種接駁方式各自可以關掉。
  - 捷運的門檻比較寬是有原因的：資料裡一個車站只有一個座標（站體中心），但實際站體長好幾百公尺、出入口分散在兩端。Pasir Ris 站中心離 Pasir Ris 廠車點 391m，但實際就是走路兩三分鐘的距離。
- **⭐ 優先候選**：對全島每個公車站牌與捷運站，跑一次「假設住在這裡」的判定，數出符合幾種**已勾選**的方式，達到門檻就給星。側欄的「住家試算」用的是同一個判定，所以點地圖看到的結論和 ⭐ 清單一定一致。
- **開關只決定「算不算數」**：直達路線、捷運可達站等等一律照算（🔁 的第二段需要用到），勾選框只決定它算不算一種可接受的通勤方式。
- **城鎮分組**：用 `config.py` 的 `TOWN_KEYWORDS` 關鍵字比對站牌 `RoadName` 粗略歸類到 HDB 鎮名，分類不準可直接編輯該表。

## 注意事項

- **base URL 必須是 `https://`**：`http://datamall2.mytransport.sg/...` 每個端點都回 404「The requested API was not found」（2026-08-24 實測）。
- 廠車點名稱是用文字比對（正規化 + token overlap ≥ 0.6）去對 LTA 的 `Description` 欄位。第一次進 app 時請看側欄每個廠車點顯示的「對到站牌 XXXXX」是否正確；對錯了可以直接在地圖上把圖示拖到正確位置（會自動吸附），或改 `config.py` 的 `match_text`。
- `Jurong East Private Bus Pickup/Drop-off Point` 很可能是公司私人接駁點、不是公開 LTA 站牌，比對很可能失敗。失敗時側欄會顯示「未對到公車站牌」，該點就不會有 N 站可達分析——直接把它拖到實際上車的那個公車站牌即可。
- 在 app 裡改的設定不會自動寫回 `config.py`；按「儲存目前設定」是存到 `data/processed/setup.json`，`main.py` 也讀同一個檔（沒有才用 `config.py` 的種子值）。但 CLI 產生的 `map.html` 與 `candidates.csv` **只算公車直達＋一站到廠車點**，捷運、轉乘、多站接駁只在探索器裡（web app 與單檔版 `explorer.html` 都有）。
- **`config.py` 的 `RAIL_LINES` 只列已通車的線**。OneMap 連還在蓋的線也會回傳站點，放進來會生出根本不存在的行程 —— 環島線（CR）目前只有四個零散的站，會讓 CR11 Ang Mo Kio 看起來可以不轉乘直達 CR4 Pasir Ris East。裕廊區域線（JS/JE）同理。**通車那天再把字首加進去，不要提前加。**
- 分鐘數是**估計值**（見「估計時間怎麼算」）：不含塞車、客滿搭不上、班次誤點，捷運轉線一律算 5 分鐘不管站內要走多遠。挑到候選區之後，請用 Google Maps 以實際出門時間對照。
- 公車班距只用早上尖峰的數字；晚班或週末通勤的人，實際等車會更久。
- CLI（`main.py`）的 ⭐ 定義是「公車直達 **且** 一站到廠車點」，所以沒有廠車點時 `candidates.csv` 的 ⭐ 是空的。探索器（含 `main.py` 產生的 `explorer.html`）不受影響。
- 英文介面的路線名稱（「3 to Punggol Int」「15 loop (via …)」）是在瀏覽器端從中文名稱改寫的；伺服器與單檔版的資料格式不變。捷運線名在 `config.py` 直接用官方英文名，兩種語言共用。
- **廠車點不要只看它吸附到哪個站牌**。側欄顯示的「已吸附到 XXX」只是最近的那一個，實際計算會用附近所有站牌。這是刻意的：`Aft Pasir Ris St 53` 最近的站牌是 `Blk 582`，而 `Blk 582` 只有 15/15A 經過、還排在第 2 站 —— 只認這一個站牌的話，接駁放得再寬也永遠只有 1 個站牌到得了。改成看 300m 內全部站牌之後，同一個上車點在「最多 8 站」的設定下可達 112 個站牌（2026-08-24，當時接駁還用站數計）。
- Leaflet 已收進 `webapp/static/vendor/`，不走 CDN；但**地圖底圖與地址搜尋（都是 OneMap）仍需要網路**，兩種跑法都一樣。底圖原本用 CARTO，2026-09-22 起它的每張圖磚都印上「API KEY REQUIRED」，所以換成新加坡土地管理局的 OneMap 灰色底圖（免 key）。
